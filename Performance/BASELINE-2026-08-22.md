# Baseline profile — 2026-08-22

This is a baseline for the typed context workload. It is kept as a text report;
the binary `.trace` bundle is not checked into the repository.

## Run

```text
RECORDS=2000 ITERATIONS=4 PAGE_SIZE=200 WARMUP=1 \
  OUTPUT_DIR=/tmp/ckswiftdata-profile-baseline \
  ./Scripts/profile_ckswiftdata.sh
```

Environment: Xcode 27.0 (27A5237l) and macOS 27.0 (26A5416b) on a MacBook Pro.
The executable was built in release mode. The client
was `CKSwiftDataTesting.InMemoryCloudDatabaseClient`, so these numbers measure
local schema/snapshot/context work and exclude CloudKit network latency.

## Wall-clock baseline

| Phase | Iteration 1 | Iteration 2 | Iteration 3 | Iteration 4 | Median | Mean |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Typed fetch, 10 pages / 2000 models | 312.390 ms | 314.070 ms | 335.264 ms | 298.938 ms | 313.230 ms | 315.166 ms |
| Typed save, 2000 bound models | 22.560 ms | 38.848 ms | 22.367 ms | 23.373 ms | 22.967 ms | 26.787 ms |

The corresponding `Fetch` and `Save` `os_signpost` intervals in
`tables.xml` agree with the benchmark's wall-clock output.

## Time Profiler findings

The trace was recorded with Time Profiler plus `os_signpost`. After selecting a
measured interval, the useful call-tree filters are Separate by Thread, Hide
System Libraries, and Invert Call Tree.

### Fetch

Across the four measured intervals, the target process accumulated roughly
264–297 ms of sampled CPU time per fetch:

- `CloudPersistentModel<>.cloudRecordSnapshot(in:)` accounted for roughly
  199–238 ms of inclusive target samples (about 75–80%).
- `CloudPersistentModel<>.cloudModelSchema()` accounted for roughly 100–127 ms
  of inclusive samples. It is nested under snapshot creation, not additional
  time on top of it.
- `CloudModelContext.captureModelFieldsForFetch()`,
  `captureDirectModelEditsRelativeToCurrentSnapshots()`, and
  `captureDirectModelEditsMadeSince(_:includingDirtyModels:)` each repeatedly
  reach model snapshot conversion while the fetch is in flight.
- `CloudRecordValue.fromCloudKit` and identifier/schema validation are visible
  leaf work, but are materially smaller than repeated snapshot/schema creation.

### Save

The measured save intervals accumulated roughly 22–29 ms of sampled CPU time:

- `CloudPersistentModel<>.cloudRecordSnapshot(in:)` accounted for roughly
  16–18 ms.
- `CloudModelContext.stageBoundModels(assets:)` accounted for roughly 10–14 ms.
- Schema/model identifier construction remains visible in the save path and
  is nested under repeated snapshot conversion.

## Optimization hypotheses

These are hypotheses drawn from the trace:

1. Cache the generated model schema and model identifier per model type instead
   of rebuilding them for every bound model snapshot.
2. Reuse one captured snapshot set across the three typed-fetch edit-preserving
   passes where their consistency rules allow it; this would reduce repeated
   `cloudRecordSnapshot(in:)` calls.
3. Re-run the same release workload after each change and compare both the
   signpost wall-clock median and the filtered Time Profiler stack. A change is
   not an improvement if it only moves work outside the selected interval.
4. Profile a real CloudKit/device path separately before making network or
   battery claims; this baseline deliberately excludes transport behavior.

## Optimization results

After the initial four-iteration trace, each optimization was measured with
the same release workload: 2000 records, 20 measured iterations, two warmups,
200 records per page, and `editStride=10`. The first row below is the
pagination baseline after removing the in-memory client's repeated full sort;
the later rows are cumulative.

| Checkpoint | Fetch median | Fetch p95 | Save median | Save p95 | Change |
| --- | ---: | ---: | ---: | ---: | --- |
| Cached pagination order | 295.281 ms | 303.026 ms | 23.826 ms | 24.848 ms | Cache the in-memory client's canonical ID order and invalidate it after mutations |
| Deduplicated fetch capture | 216.361 ms | 223.291 ms | 23.744 ms | 25.190 ms | Reuse one start snapshot pass while preserving in-flight edit reconciliation |
| Schema cache | 111.183 ms | 117.617 ms | 12.550 ms | 13.027 ms | Cache validated schema per model metatype |
| Schema and identity cache | 90.424 ms | 93.563 ms | 9.529 ms | 10.243 ms | Cache default model identity validation per metatype |
| Save snapshot reuse | 92.067 ms | 94.846 ms | 7.370 ms | 8.078 ms | Reuse pre-await snapshots for staging and post-save snapshots for re-stage |
| Cache contract opt-in | 91.412 ms | 94.051 ms | 7.291 ms | 8.848 ms | Keep the fast cache for macro models; rebuild custom dynamic declarations |
| Proven macro expressions | 85.564 ms | 91.831 ms | 7.231 ms | 8.121 ms | Opt in only when record/schema/relationship expressions are proven stable |
| Stricter macro cache guard | 84.903 ms | 91.647 ms | 7.176 ms | 7.781 ms | Require explicit plain `recordType`, syntax-level literals, and context-specific option/delete-rule members |

The last three rows tighten the cache contract; their fetch medians remain
within normal run-to-run variance. Relative to the first row,
the final cumulative result is about 71% lower fetch median and 70% lower save
median. Relative to the original four-iteration report, the fetch phase fell
from a 313.230 ms median to about 86 ms and the save phase from 22.967 ms to
about 7 ms. These percentages describe this deterministic in-memory workload, not
CloudKit network latency.

### Final Time Profiler evidence

A final trace recorded after these changes measured 82.989, 91.289, 85.021,
and 91.569 ms for fetch, and 6.646, 7.166, 7.581, and 7.466 ms for save.
After schema and identity caching, schema construction and identifier
validation no longer appear as material hot frames. Fetch samples are now
dominated by `captureFetchStartState`,
`captureDirectModelEditsMadeSince(_:includingDirtyModels:)`, snapshot value
bridging, and `makeCapturedEdit`. Save samples show
`stageBoundModels(assets:snapshotsAtSaveStart:)` and one remaining snapshot
bridge as the meaningful remaining work.

### XCTest performance evidence

The synchronous XCTest snapshot test passed under strict concurrency at every
checkpoint. The Release run (`swift test -c release`) measured a
clock average of 1.83 ms, CPU time of 2.08 ms, and 36,423 kI retired
instructions; peak physical memory averaged 12,345 kB. The earlier 5.5–6.0 ms / 119,000 kI
figures were Debug measurements and are not representative. Physical-memory
samples have high variance, so memory is retained as an observation rather than a
regression gate.

The XCTest output reported `baselineName: ""`, and this repository has no
checked-in `.xcbaseline`. The test therefore measures and reports performance
but does not automatically fail on a historical regression until a baseline is
configured in Xcode.

### Cache contract

The runtime identity/schema cache is safe for the macro-generated models: their declarations are deterministic type-level values. Custom
`CloudKitModel` conformers now default
`cloudModelRuntimeMetadataIsStable` to `false`, so their static declarations
are rebuilt instead of being frozen by this process-local cache. The macro sets
the marker to `true` only for an explicit plain string `recordType`, an omitted
or integer-literal `schemaVersion`, and syntax-level literal schema arguments.
Attribute option and relationship delete-rule shorthand is accepted only in
its corresponding typed position. Computed, interpolated, qualified, or
otherwise uncertain expressions—and models without an explicit record type—opt
out conservatively.
